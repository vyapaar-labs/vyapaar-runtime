# 0005 — REST API OpenAPI 3.1 Specification Completeness, Schema Coverage, and Artifact Export

**Status**: open

## What's stubbed or hardcoded

The REST API layer (`vyapaar-runtime-api-rest`) exposes OpenAPI 3.1 specifications dynamically at `/schema/openapi/v1.json`, `/schema/openapi/v2.json`, and `/schema/openapi` (with Swagger UI at `/docs` and `/swagger-ui`), generated by `crates/vyapaar-runtime-api-rest/src/openapi.rs`. However, the specification is incomplete, partially disconnected from active router definitions, and lacks automated contract export:

1. **Missing Route Definitions in OpenAPI Document**:
   Multiple active routes in `crates/vyapaar-runtime-api-rest/src/v1.rs` are omitted from `openapi.rs`:
   - All 10 `/reports/*` endpoints (`/reports/ledger`, `/reports/tax`, `/reports/snapshots`, `/reports/audit`, `/reports/concentration`, `/reports/wac`, `/reports/fees`, `/reports/equity-curve`, `/reports/fills/:order_id`).
   - Legacy report aliases (`/ledger`, `/tax/report`, `/fees`, `/positions/audit`).
   - `/bars` (`POST` ingest endpoint for tick/bar ingestion).
   - `/trading-state` (`PUT` handler for runtime state transition).
   - Order approval workflow endpoints (`/approval/queue`, `/approval/approve`, `/approval/reject`).
   - WebSocket streaming upgrade routes (`/ws`, `/ws/market`).

2. **Incomplete Request and Response Component Schemas**:
   In `openapi.rs`, `components.schemas` only registers 9 core types (`InstrumentId`, `OrderSide`, `OrderStatus`, `OrderType`, `Price`, `Quantity`, `TimeInForce`, `RiskLimits`, `RiskRefusal`). The following wire models are missing typed schemas:
   - `ResponseEnvelope<T>` and standard error envelopes (`ErrorDetail`, `ErrorCode`).
   - Market data DTOs (`QuoteTick`, `QuotesResponse`, `BarsResponse`, `DepthResponse`, `DepthLevel`).
   - User profile DTOs (`Profile`, `Module`, `LayoutConfig`).
   - Screener models (`ScreenerQuery`, `ScreenerResultRow`, `ScreenerResponse`).
   - Performance journal DTOs (`TradeJournalTradeRecord`, `TradeJournalAccountRecord`, `TradeJournalNoteRecord`, `TradeJournalCalendarResponse`, `TradeJournalCompareResponse`).
   Operations define generic string summaries instead of referencing concrete `components.schemas` entries.

3. **Missing Static OpenAPI Artifact Generation**:
   There is no build-time or CI task that exports the generated OpenAPI specification to a static file (e.g. `schema/openapi.v2.json`) for consumption by frontend client code generators, SDK generators, or API documentation pipelines.

4. **Lack of Automated Contract Drift Tests**:
   No test suite verifies that every Axum route declared in `v1::router()` / `v2::router()` has a corresponding operation entry in `OpenApiDocument::generate_v2()`, or that serializations produced by live handlers match the declared schemas.

## Why

The OpenAPI generator in `openapi.rs` was originally added as a self-contained module using manual `BTreeMap` insertion and `schemars` reflection for a subset of endpoints during early platform scaffolding. As new domains (reports, screener, trade journal, market reference) were implemented in `vyapaar-runtime-api-rest`, their Axum routes were registered in `v1.rs` without updating `openapi.rs` in tandem. Without automated contract-linting or consumer codegen, the schema drift remained unnoticed until frontend client integration.

## How to close it

1. **Complete OpenAPI Path and Operation Coverage**:
   Update `crates/vyapaar-runtime-api-rest/src/openapi.rs` to register all active endpoints from `src/v1.rs`:
   - Add path items and parameter/request-body specs for `/reports/*`, `/trading-state`, `/bars` (POST), `/approval/*`, and `/ws`.
   - Ensure operation IDs follow uniform camelCase conventions (`getReportLedger`, `postIngestBars`, etc.).

2. **Populate Component Schemas with `schemars`**:
   Derive `schemars::JsonSchema` for all wire types in `vyapaar-runtime-api::wire`, `vyapaar-runtime-api::profile`, and `trade_journal.rs`. Register them in `components.schemas` and link operation request/response bodies to `$ref: "#/components/schemas/<TypeName>"`.

3. **Export Static OpenAPI Document in CLI / Build**:
   Expose a CLI command (e.g. `vyapaar schema --openapi --v2 > schema/openapi.v2.json`) and configure a cargo test or build script to write and verify the checked-in schema artifact.

4. **Add Router-OpenAPI Conformance Tests**:
   Implement an automated unit test in `crates/vyapaar-runtime-api-rest/tests/` that reflects over the Axum route table (or checks route constants) against `OpenApiDocument::generate_v2().paths`, ensuring 100% route coverage and preventing future schema drift.
